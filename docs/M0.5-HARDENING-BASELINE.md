# M0.5 — Hardening and Performance Baseline

## Scope

M0.5 hardens the existing in-memory core without introducing a storage backend or changing the unresolved M0.4 backend-failure contract.

Included:

- adversarial boundary and state-preservation tests;
- dense overlay and restore coverage;
- a reproducible Rust toolchain pin;
- a small release-mode performance baseline for the existing in-memory operations.

Excluded:

- persistence;
- filesystem or block-device access;
- storage traits or backend abstractions;
- kernel, driver, or OS integration;
- networking;
- changes to commit failure semantics.

## Hardening coverage

The added tests exercise:

- BlockId::new(usize::MAX) read/write behavior;
- preservation of existing state after a rejected write;
- dense diff coverage across every block;
- dense restore back to a checkpoint;
- preservation of committed state through later discard/restore operations.

The intent is to strengthen executable invariants without changing the core model.

## Reproducibility

The repository now pins Rust to 1.98.1 in rust-toolchain.toml, matching the verified local development toolchain used for this milestone. CI installs the same toolchain before running formatting, tests, Clippy, and the performance baseline.

This pin is deliberate rather than a claim that it is the newest stable compiler.

## Performance baseline

src/bin/m0_5_baseline.rs measures six deterministic in-memory scenarios in release mode:

- read
- write
- checkpoint
- diff
- write+restore
- write+commit

Each scenario uses fixed block counts and iteration counts with a warm-up phase and reports total elapsed nanoseconds plus nanoseconds per operation.

The baseline is a measurement instrument, not a performance gate. Results depend on the runner CPU, operating system, compiler, and system load, so M0.5 does not impose a hard timing threshold. Regression thresholds can be introduced later once repeated measurements exist on a controlled runner.

## Validation contract

The milestone is considered technically clean only when:

- cargo fmt --all -- --check passes;
- cargo test --all-targets passes;
- cargo clippy --all-targets -- -D warnings passes;
- the release-mode baseline binary exits successfully;
- a second audit confirms that the diff remains inside M0.5 scope.

## Architectural boundary

M0.4 remains a decision gate. No storage interface is added here, and no decision is made about atomic versus partial backend commit failure. Storage work remains blocked until that contract is explicitly decided.
