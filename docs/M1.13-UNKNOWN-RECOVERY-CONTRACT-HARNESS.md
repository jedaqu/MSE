## Problem

The backend-neutral persistence contract explicitly defines `CommitOutcome::Unknown` as an outcome whose publication result cannot be established. The contract requires the prepared state and the same `TransactionId` to remain available for reconciliation or retry.

The reusable backend contract harness currently exercises:

- successful `Committed` publication;
- `Aborted` retention and retry;
- reconciliation of committed and aborted transactions;
- rejection of durability observations for `Aborted` and `Unknown`.

It does **not** exercise a backend entering the `Unknown` state and then being reconciled or retried through the same transaction identity.

M1.12 closed reconstruction/recovery coverage, but its recovery scenarios start from a committed transaction or an uncommitted prepared transaction; they do not close the uncertainty gap.

## Evidence

1. M1.7 contract: `Unknown` must preserve the same `TransactionId` and require reconciliation/retry rather than being silently converted to `Aborted`.
2. M1.8 contract: `Unknown` retains the target generation for reconciliation and cannot authorize a durability claim.
3. M1.11 harness: current reusable coverage contains no execution path that produces and reconciles an `Unknown` outcome.
4. `PersistenceBackend::commit` already exposes `Unknown` as a valid semantic result, so the missing capability is behavioral coverage rather than a missing production API.
5. `FileBackend` contains an `Unknown` return path when publication cannot be confirmed, while its existing tests do not exercise that path end-to-end.

## Objective

Add reusable, deterministic contract coverage proving that an `Unknown` outcome:

- preserves the original `TransactionId`;
- preserves the target generation;
- does not become `Aborted` merely because publication is uncertain;
- can be reconciled against the same logical transaction;
- can be retried without silently creating a second independent transaction.

## Scope

- Extend the existing backend contract test infrastructure.
- Add only the minimum test-only mechanism required to produce a deterministic `Unknown` scenario.
- Validate the semantic behavior through `PersistenceBackend` and existing core types.
- Preserve the existing M1.7/M1.8 meanings of `Committed`, `Aborted`, `Unknown`, `TransactionId`, and `Generation`.
- Keep the implementation suitable for future backends without requiring physical-storage knowledge in the semantic harness.

## Non-scope

- No new physical backend.
- No Linux/Windows/Android adapter.
- No filesystem, block-device, kernel, driver, networking, or distributed-coordination layer.
- No universal constructor or backend lifecycle abstraction.
- No change to the public semantic contract unless implementation evidence proves the existing contract is insufficient.
- No production fault-injection API unless the audit proves a test-only alternative cannot satisfy the criterion.
- No product-layer work.
- No branch-protection or other administrative changes.

## Dependencies

- Existing `PersistenceBackend` contract.
- Existing `CommitOutcome::Unknown` semantics.
- Existing `TransactionId` and `Generation` types.
- Existing M1.11 contract harness.
- Existing M1.12 recovery harness and current CI structure.

## Risks

- A test fixture could accidentally test the fixture rather than the backend contract.
- A failure-injection mechanism could leak into production API surface if not kept test-only.
- The harness could accidentally redefine `Unknown` semantics instead of testing the already-established contract.
- An unnecessarily broad abstraction could be introduced to make the test easier.

## Minimal-change rule

Prefer a test-only fixture or seam over any production abstraction. Do not modify `PersistenceBackend` unless the implementation audit demonstrates that the existing contract cannot express the required test.
