# M1.7 commit and recovery contract

## Status

M1.7 defines the transaction/commit/recovery contract only. No persistent backend is implemented.

## Identities

### TransactionId

`TransactionId` identifies one logical commit attempt.

The current implementation generates an opaque process-local numeric identity. It is sufficient for in-memory reconciliation tests, but its durable representation across process restart remains a future backend responsibility.

### Generation

`Generation` identifies a logical committed state sequence.

A successful commit publishes one target generation from one base generation. Generations are monotonic logical values in the current model.

## Prepared state

`PreparedState` is the immutable contract boundary between preparing a transaction and attempting publication.

It retains:

- one `TransactionId`;
- the committed base `Generation`;
- the target `Generation`;
- the complete `ChangeSet`.

Preparation does not make the target state visible as committed.

## Atomic visibility

Logical commit is atomic at the publication point.

For a transaction prepared from generation `N` for generation `N+1`, observers may see:

- committed generation `N`, or
- committed generation `N+1`.

They must never observe a partially published mixture that is presented as the committed generation.

A backend may perform multiple physical writes before publication. Those writes are preparation material, not committed visibility.

## Observable outcomes

The contract exposes exactly three outcomes:

| Outcome | Meaning | Required pending-state rule |
| --- | --- | --- |
| `Committed` | Publication of the target generation is known to have occurred. | Transaction may become terminal and its retained preparation may be released after reconciliation is complete. |
| `Aborted` | Publication of the target generation is known not to have occurred. | Prepared state remains available until explicitly discarded. |
| `Unknown` | The caller cannot establish whether publication occurred. | Prepared state must be retained; reconciliation must use the same `TransactionId`. |

`Committed` describes logical publication. It does not, by itself, claim that a backend has crossed its physical durability boundary.

## Durability boundary

Durability is distinct from logical visibility.

The future backend contract must explicitly state the point at which a published generation is considered durable against the backend's supported failure model. M1.7 does not select a journal, copy-on-write layout, filesystem primitive, or device-specific mechanism.

## Failure-point matrix

| Failure point | Required interpretation |
| --- | --- |
| Before preparation | No committed transition exists; no transaction needs recovery. |
| During preparation | Target generation is not visible; retain or abort the prepared transaction according to the backend's evidence. |
| After data preparation but before publication | Target generation must remain invisible; if publication is proven absent, outcome is `Aborted`. |
| At publication with uncertain result | Outcome is `Unknown`; do not create a second independent transaction. |
| After publication with positive confirmation | Outcome is `Committed`. |
| After publication with uncertain observation | Outcome is `Unknown` until reconciliation establishes the result. |

## Reconciliation and retry

`Unknown` is not equivalent to `Aborted`.

Recovery must first reconcile the existing `TransactionId`:

1. If the transaction is found published, resolve it as `Committed`.
2. If it is proven unpublished, the same prepared transaction may be retried.
3. A retry must not silently allocate a second independent transaction for the same logical commit attempt.
4. Until reconciliation is complete, the prepared state remains retained.

For `Aborted`, the prepared transaction remains recoverable until explicitly discarded. After explicit discard, a new transaction may be created.

## Explicit non-goals

M1.7 does not define:

- a storage trait;
- a persistent object store;
- a journal or write-ahead log;
- a filesystem or block-device integration;
- a durable transaction identifier encoding;
- a recovery database;
- a driver, kernel module, or operating-system adapter;
- network coordination.

Those decisions belong to later milestones after this contract is validated.

## Acceptance gate for M1.8

Before any persistent backend is introduced, the next milestone must preserve this contract and add only the minimum backend-neutral durability/reconciliation boundary needed by the selected backend experiment.
