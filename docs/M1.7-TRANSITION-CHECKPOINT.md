## M1.7 delivered

The public core now defines the contract needed before any persistent backend is designed:

- `TransactionId` identifies one logical commit attempt;
- `Generation` identifies a logical committed-state sequence;
- `PreparedState` freezes the transaction identity, source generation, target generation, and `ChangeSet`;
- `CommitOutcome` exposes `Committed`, `Aborted`, and `Unknown`;
- logical commit visibility is atomic at publication;
- `Unknown` retains the prepared state and transaction identity for reconciliation;
- durability is explicitly separate from logical publication.

## Boundary verified before transition

M1.7 remains backend-neutral and in-memory. It introduces no persistence, storage trait, journal, filesystem or block-device integration, physical-address model, kernel or driver code, operating-system-specific adapter, networking, or durable transaction identity encoding.

## Next phase gate

M1.8 may define the minimum backend-neutral persistence/durability boundary required for the first storage experiment.

M1.8 must preserve the M1.7 rules for atomic visibility, `Committed` / `Aborted` / `Unknown`, pending-state retention, and reconciliation by the same transaction identity.

No concrete persistent backend is authorized by this checkpoint until that boundary is audited.
